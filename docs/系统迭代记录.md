# RSI System Iteration Log

Every version change below was driven by evidence from the previous run; each entry records why the change was made. The pilot run `runs/pilot` resumes from saved state, so the changes were applied as successive generations without restarting the experiment. All candidates' results remain in `state.json`.

## v0 → v1: getting the pipeline running (2026-10-21 early morning)

| Problem | Evidence | Fix |
|---|---|---|
| Training was 20× slower than expected | VRAM pegged at 24 GB, power draw only 110 W, process working set 26 GB | On Windows the driver silently spills to system RAM. Added `torch.cuda.set_per_process_memory_fraction(0.9)` so it fails fast instead. Gradient checkpointing on by default. The LM head + cross-entropy run only on response tokens, chunked (2048) with recomputation |
| After fine-tuning the model **never stopped** | Finish rate 0%. Labels contained `<|im_end|>`, but P(`<|im_end|>`) ≈ 0 both before and after SFT | Qwen3-Base's tied `<|im_end|>` embedding is effectively untrained, so LoRA cannot make it the top prediction. Switched the response terminator to `<|endoftext|>`, which the base model already uses. Finish rate went from 0% to 95% |
| Let the base model generate its own data from gen 1 | Base already gets 26.5% strict instruction-following and 72.7% GSM8K on test, and partly follows ChatML | `synth_from_base: true`: gen 1 starts self-generation directly, with no hand-built bootstrap data |

## v1 → v2: selection and repair (after gen 1)

Evidence: in gen 1, both candidates had **P(better) = 1.00** on the composite score (dev strict instruction-following 23.5% → 34.5–38.0%, degeneration 24% → 7%), but GSM8K fell 74.0% → 68.0% / 69.3%, which tripped the 3-point math guard.

1. **Selection bug**: v1 picked the highest-composite candidate first and only then applied the gate. If that candidate failed while another passed, nothing was promoted. Now the best is chosen **among gate-passing candidates**.
2. **Failure-directed repair**: a candidate that is clearly better but blocked by a guard is a "near-miss". In the next generation, half the candidates use it as the parent and may only apply "repair operators" matched to the failure type (math regression → lower LR, fewer epochs, less external data, more self-generated data …). Which repair is tried is still decided by Thompson sampling.
3. Candidates per generation raised from 2 to 3.

## v2 → v3: parent choice and data ablation (after gen 2)

Evidence: all 3 candidates in gen 2 failed the math guard again (66.7% / 68.7% / 70.7%). The lower-LR repair (70.7%) missed by just 0.3 points, but v2 had used the highest-composite candidate (68.7%) as the parent.

1. The repair parent is now the **candidate closest to passing** (smallest guard violation), not the one with the highest composite score.
2. Added **data-source ablation** operators, "drop math gold" and "halve seed data". They test directly whether the regression comes from some external data source, rather than tweaking hyperparameters only.

## v3 → v4: self-distilled seed data (after gen 3)

Evidence: across 3 generations and 8 candidates, every SFT recipe lost 3–13 points of math (lowest 60.7%). Changing LR, epochs, rank or data volume did not fix it. Halving the seed data actually made it worse. Conclusion: the problem is not the hyperparameters but **the target answers come from outside the model's distribution**. The answers in alpaca and GSM8K gold are terser and differently styled than the model's own, and imitating them weakens its native step-by-step reasoning.

1. Added a **self-distilled seed** data source (SDFT idea): the champion answers seed instructions itself with greedy decoding; answers that don't terminate, repeat, or echo the prompt are dropped. The new gene `seed_source ∈ {alpaca, self}` plus the operator "self-distilled seed" was added to the math repair set. Training data can then be **entirely generated by the model itself plus programmatic rules**, which is closer to the spirit of RSI.
2. **Data engine caps**: after two failed promotions in a row, self-generation scale had grown to 1,562 prompts × 8 samples (~50 minutes). Now capped at ≤1,200 prompts and k ≤ 8.
3. **Untried operators first** (added during gen 4): replaying gen 4's proposals offline showed that Thompson sampling did not pick the newly added "self-distilled seed" operator. A fresh Beta(1,1) arm only gets chosen by chance against arms whose posteriors have already moved. Now each candidate first takes one allowed operator that has never been tried (no two sibling candidates take the same one), and Thompson sampling fills the rest.
4. **No-op operator filtering**: for example, applying "use external seed answers" to a recipe that already uses external seeds changes nothing. Such operators are dropped so they are never credited with another operator's result.
5. **Self-generation checkpoint**: each generation's self-generation stats are written to `gen_XXX/synth.json`, so a restart mid-generation no longer re-runs the ~55-minute self-generation step.

## v4 → v5: the real root cause, STaR shortest-chain selection bias (after gen 5)

Evidence: gen 5 got the forced trials of "drop math gold" (math 68.7%) and "self-distilled seed" (math **62.7%**, worse still). **The system's own experiments refuted the v4 hypothesis that out-of-distribution external answers were the cause.** Next I compared base vs. candidates directly on the dev items where the base was right and the candidate wrong:

- Every lost item was a "wrong value", not formatting or truncation.
- The candidate's **median reasoning length fell from 217 tokens to 117–138**, and some answers were only `The answer is 540.` with no steps at all.
- Cause: in v1–v4 STaR kept the **shortest** of the k correct samples. With 8 samples a bare guess is sometimes right by luck, and it is always the shortest, so it got selected. 152 of the 1,403 self-generated math solutions in the pool (11%) are such shortcuts, and their count rose with k (7 at k=4 → 32–44 per generation at k=6–8). **The data engine's "low pass rate → raise k" feedback rule amplified the bias.**

Fixes:
1. `valid_math_chain`: a solution must show its work before the final answer (≥25 words and ≥2 arithmetic steps). Calibration: keeps 106/111 (95%) of the base model's genuine correct solutions and rejects all 152 shortcuts.
2. Among valid solutions, take the one closest to the **median length** instead of the shortest.
3. **Retroactive cleanup**: when training sets are built, old pool rows are filtered with the same check.
4. Time budget: the self-generation cap was lowered to 800 prompts per generation (the pool already has 1,500+ verified instruction samples).

Lesson: in a self-improving loop, **selection rules over self-generated data are themselves an optimization pressure**. "Shortest correct" looks harmless but systematically rewards guessing. A verifier that checks only the final answer is not enough; the process has to be checked too.

## v5 → v6: verifier gaming (after the gen-6 promotion)

Evidence: while picking a showcase for the deck, I noticed the champion answered one all-caps + no-comma + postscript prompt with only `P.S.`. It passes all 3 format checks without doing the task at all. Measured on test: strict passes with fewer than 15 words are 13/200 for the base and 16/200 for the champion. In the self-generated instruction pool, 277/1,821 samples are under 15 words. Some are legitimate (word-limit or JSON constraints); others are hacks like `[address]` alone. The base model's prompt echoes also "pass" the keyword check incidentally.

Fixes:
1. `substantive`: self-generated answers must have ≥20 words (only "word_max / json" constraints allow ≥5). Applied to new samples and **retroactively** to the pool.
2. New **robust metric** `if_prompt_acc_substantive` (strict accuracy over substantive answers only), shown in reports, the PPT and the demo. **It does not enter the gate composite**, so generations before and after stay comparable.
3. The PPT sample picker shows only champion answers with real content (40–110 words).

Robust view on test: strict accuracy for base → gen-6 champion is **21.5% → 26.5% (+5.0)**, compared with +8.0 by the raw metric. Both numbers are reported.

## v6 → v7: winner's curse (seen in gens 7 and 8; fixed from gen 9 on)

Evidence: the gen-6 champion was selected by its dev score, so its dev math of 85.3% is optimistically biased (its independent test score is only 79.3%). Gen 7's best challenger: dev math 82.0%, P(better) = 0.72. Gen 8's best challenger: dev math 80.7%, P(better) = 0.63. Both were blocked by "math regression > 3 points", but part of that regression is just the champion's lucky draw. As long as the champion keeps its selected dev score as the bar, every challenger is compared against a number inflated by selection.

Fix (`rsi/data.py: gate_set`, `rsi/loop.py: gate_eval`):
1. Each generation generates a **fresh gate set**: the 200 held-out dev tasks with freshly sampled constraints (deterministic per generation, so restarts don't change it), plus a rotating slice of 150 GSM8K test items that dev and test never use (pool of 1,019).
2. The **champion and every candidate** are evaluated on that generation's gate set. The paired bootstrap, the guard metrics, near-miss detection and bandit credit all use gate-set results; dev keeps only the fixed curves and diagnostics.
3. Cost: one extra evaluation per model per generation (~2–3 minutes each). Restarts reuse the per-model gate results.

Not changed: the gate criteria themselves (Δ>0, P ≥ 0.8, math −3 / degeneration +3). test is still not used for any decision.

**Result in its first generation (gen 9)**: the gen-6 champion scored a composite of **0.5447** on fresh items, versus its dev selection score of 0.5703. Math was **76.0%**, versus 85.3% on dev, which confirms a winner's curse as large as 9 points. The challengers c0 = 0.5671, c1 = 0.5419, c2 = 0.5861. c2 (epochs↑ + LR↑) was promoted: Δ = +0.041, P = 0.97, 90% CI [+0.007, +0.076]. On the independent test set, gen 9 scored strict instruction-following **48.0%** (base 26.5% / gen 6 34.5%), per-constraint 64.5%, GSM8K **82.7%** (base 72.7%), and degeneration 6.9%. This is the second promotion, and gen 9's training data was generated by the gen-6 champion, so the recursion is compounding.

## Gen 10: a promotion that passed the gate but didn't transfer (caveat)

Gen 10's candidate c2 (seed data↑) passed the gate: on the gate set, composite was 0.6150 vs the champion's 0.5876, Δ = +0.027, P = 0.97, **but the 90% CI lower bound was only +0.002**. On the independent test set, **every gen-10 metric is slightly below gen 9**: strict instruction-following 46.0% vs 48.0%, robust view 40.0% vs 41.5%, GSM8K 80.7% vs 82.7%, degeneration 9.1% vs 6.9%. All of this is within noise. The right reading is **"same level as gen 9, not confirmed better"**.

Lesson / next step (v8 proposal, not yet implemented):
- "P(better) ≥ 0.8" only constrains direction, not size. Small effects can pass by noise. Add a **minimum effect size** (e.g. CI90 lower bound > 0, or Δ ≥ 0.01), or require the newly promoted model to **pass again on a second fresh gate set** (a confirmatory gate).
- The IF part of the gate set reuses the same 200 dev tasks (only the constraints are re-sampled), so the effective sample size is smaller than it looks. A larger task pool is worth considering.
- test is still not used for any decision. This caveat comes from test but is reported only and does not feed back into the gate.

## Qualitative findings from the live demo (13:15, gen 10 vs base, one sample)

Task: "Write a short introduction to the Great Wall of China for tourists" + `<<title>>` + exactly 5 bullet points + P.S. On this single sample the base passed all three checks, while gen 10 missed the P.S. A single sample is noisy, but it surfaced two real quality issues:
1. **Rule augmentation leaks an unnatural style**: gen 10's title was `<<write a short introduction to the great wall of china for tourists>>`, i.e. the instruction lowercased, which is exactly the template `Constraint.apply("title")` uses when rewriting data. The model learned to "use the instruction as the title". Fix: have rule augmentation generate the title from the answer content (or let the champion generate the title and verify it), and/or reduce the weight of `rule` data.
2. **The postscript was written as a list item** (`* P.S. …`), so the check (P.S. must start a line) rejected it. That is a real failure to follow the instruction (P.S. belongs after the body), and it shows conflicts between combined bullet + postscript constraints are under-represented in training. Raise the curriculum weight for that combination.

## Third-party check: official IFEval (2026-10-21 09:41–10:02)

In-house verifiers and the training data come from the same constraint library, so to rule out "learning only our own checks", the official **google/IFEval** (541 prompts, lm-eval `ifeval.utils.process_results`, ChatML + greedy, max 1,280 tokens) was run separately. Its constraint set is only partly the same as ours (`repeat_prompt`, `response_language`, `letter_frequency`, `nth_paragraph_first_word` and others never appear in training). Results in `runs/pilot/ifeval_official/summary.json`:

| Metric | Base | Gen-6 champion | Δ |
|---|---|---|---|
| prompt-level strict | 24.4% | 35.7% | **+11.3** (paired bootstrap 90% CI [+7.6, +14.8], P = 1.00) |
| instruction-level strict | 37.4% | 48.1% | +10.7 |
| prompt-level loose | 26.8% | 38.1% | +11.3 |
| Finish rate | 31% | 74% | |

Breakdown by whether the instruction type appears in training (the 16 IFEval types that map to our 18 kinds count as "seen"; the other 9 never appear in training):

| Group | Base | Gen 6 |
|---|---|---|
| Seen types, inst strict (n=564) | 38.3% | 50.0% |
| **Unseen types**, inst strict (n=270) | 35.6% | **44.1%** |
| Prompts with only unseen types, prompt strict (n=117) | 30.8% | 40.2% |
| prompt strict excluding passes under 20 words | 19.8% | 28.3% |

Conclusion: the instruction-following gain **transfers to an independent third-party benchmark, including instruction types never trained on**, so it is not just familiarity with our own templates. The IFEval gain (+11.3) is larger than the in-house test (+8.0 raw / +5.0 robust).

The apparent regressions `punctuation:no_comma` (72.7% → 36.4%) and `keywords:forbidden_words` (55% → 41%) were **checked item by item and are a measurement artifact**: most of the base model's passes on these are degenerate outputs (non-stopping repetition naturally contains no commas or forbidden words). no_comma: base passes 48, of which 36 are degenerate; gen 6 passes 24, of which 6 are degenerate. Counting only non-degenerate answers, gen 6 wins **18 vs 12**. forbidden_words: base 27 (19 degenerate) vs gen 6 20 (7 degenerate), so gen 6 wins **13 vs 8** on non-degenerate answers.

**Follow-up (13:04, after gens 9/10 were promoted)**: same setup, re-run on the later champions:

| Model | prompt strict | inst strict | prompt loose | Finish rate | vs base (prompt strict, 90% CI) | Unseen types inst strict |
|---|---|---|---|---|---|---|
| base | 24.4% | 37.4% | 26.8% | 31.4% | — | 35.6% |
| gen 6 | 35.7% | 48.1% | 38.1% | 74.1% | +11.3 [+7.6, +14.8] | 44.1% |
| gen 9 | 42.0% | 53.0% | 45.3% | 82.6% | +17.6 [+13.5, +21.6] | 47.4% |
| gen 10 | 42.3% | 54.1% | 44.9% | 83.2% | +17.9 [+13.9, +22.0] | 50.4% |

Every step of the recursion (gen 6 → 9) shows up on the third-party benchmark too. gen 10 vs gen 9 differs by only +0.4 on IFEval, which is opposite in direction to the in-house test's −2.0. Both are within noise, consistent with the "same level as gen 9" reading above. **Reporting rule**: the headline uses the system's own champion (gen 10). Choosing which model to report by test or IFEval score would itself be selection on the test set.

Caveat: the generation format is **ChatML prefix + greedy** (same as our own evals), not lm-eval's default prompt format, so absolute values **are not directly comparable to public leaderboards**. Only the base-vs-champion comparison under the same format is meaningful. Even so, both should get more weight in the curriculum.

## Evaluation choices kept on purpose

- Even when many candidates missed the math guard by a small margin, **the gate was not loosened mid-run**. Changing the promotion criterion after seeing results is goalpost-moving and makes the reported "improvement" untrustworthy.
- test is evaluated only on the baseline and on promoted champions. All of the decisions above used only dev and run logs.
